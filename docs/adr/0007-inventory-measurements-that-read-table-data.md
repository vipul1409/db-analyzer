# Inventory: measurements that read table data, bloat as wasted space, and the inventory-analyst subagent

**Status:** accepted (#11)

Sizes, row estimates, partition and schema rollups and vacuum/analyze recency all come from the catalog (`queries/storage_stats.sql`), which the EXPLAIN gate exempts. Two inventory measurements read table data instead: a dead-tuple scan (`pgstattuple_approx`) and an exact `count(*)`. Each runs only where it is allowed, and is otherwise a **skipped measurement**.

**A skipped measurement doesn't make the Run partial.** If the gate refuses a table's exact count, the table was still measured; it just keeps its estimate. So the table stays in the Run's scope, and the reason is recorded on its snapshot (`StorageStats.skipped`). It is not added to `Run.skipped`, which would take the table out of scope and mark the Run partial (CONTEXT.md, *Skipped collection*). A refused count must not make a measured table look unmeasured, and later Run comparisons must not ask "fixed?" about its Findings. The report, the CLI and the tool results list every skipped measurement with its reason.

**The dead-tuple scan is gated by rows to read, not by its plan.** `pgstattuple_approx(t)` plans as a single function scan of one row, so the EXPLAIN gate always passes it. The statement still goes through the gate, which does nothing useful here. Before the statement runs, the scan is refused when the table's live + dead tuples (from the statistics counters) exceed the Connection's `max_scan_rows`, the same limit the gate applies to scans. A table is scanned only when its counters already suggest bloat (≥ 1,000 dead tuples and ≥ 0.2 per live tuple), and only plain tables are scanned. As a result, a table whose counters have caught up after cleanup isn't scanned, and its free space goes unseen. Without `pgstattuple`, bloat comes from the counters, and the Finding's evidence says which source it used.

**Bloat is dead tuples plus free space.** Any later read of a page prunes its dead tuples into free space. That space stays allocated until something rewrites the table. On the seeded `audit_log`, a scan by an earlier test turned 31% dead + 31% free into 0% dead + 62% free. So with a scan, the Finding measures `wasted_percent` (dead + free ≥ 30%; ~10% free is normal page slack). Without one, it measures dead tuples per live tuple from the counters.

**Exact counts are a targeted Run, opt-in.** `count_rows_exact(tables)` (and `dbx analyze --table … --exact-counts`) runs an inventory Run scoped to the named tables. Counting is measurement, and the Run records which tables it covered. The tables are counted smallest first, so that if the query cap is reached, the counts left out are the expensive ones. Once the cap is reached, every remaining count is skipped with that reason instead of failing the Run. A targeted Run records no size-ranking Findings, because a rank among two tables means nothing. `all_tables` counts every table and leaves "small" to the gate, rather than to a separate size threshold.

**New Findings in existing categories.** Index-heavy tables and oversized TOAST are `size` Findings with a rule name in the fingerprint (`size:<table>:index_heavy`, `size:<table>:toast_oversized`), as proposal §4.1 allows. Both ignore tables whose part is under 1 MiB, where a single heap page against two index pages is page rounding, not a problem. Stale statistics use rows changed since the last analyze (≥ 1,000 and ≥ 0.2 of the estimate), or a large table that was never analyzed. Findings are recorded most severe first, then by table size, and the report and tools present them in that order.

**The inventory-analyst subagent owns the storage tools.** `probe`, `get_storage_stats` and `count_rows_exact` belong to the subagent. The orchestrator keeps `probe` and `run_readonly_sql`, and delegates storage questions through deepagents' `task` tool. The subagent shares the orchestrator's middleware (turn limits, strict schemas, gateway), so its model calls hit the same privacy check, concurrency cap, request log and cassette. `NewTurn` stays on the orchestrator only, because it would otherwise reset the query cap mid-Turn. A subagent's tool and SQL events reach the stream only with `astream(..., subgraphs=True)`. `Translator` takes the namespace: inside a subagent, tool and SQL events pass through, but its text is a report to the orchestrator and doesn't become the answer. Proposal §6.1's `list_collections` isn't built, because `get_storage_stats` already lists the largest tables, schema totals and Findings.

## Considered Options

- **Gate-rejected count → `Run.skipped`:** rejected. It would take a measured table out of scope and make every Run with one refused count partial.
- **Scan every table with `pgstattuple_approx`:** rejected. That is one statement per table against a 50-per-Turn query cap, and it reads data for tables the counters already show as clean.
- **Keep `get_storage_stats` on the orchestrator as well:** rejected for now. The ticket gives the tools to the subagent. A quick "biggest tables?" now costs a delegation (two more model calls), and the M7 evals can revisit that.
